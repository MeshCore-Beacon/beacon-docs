# Beacon end-to-end audit — 16 November 2026

## Purpose and decisions

This audit reconciles the upstream repositories, their development and release
branches, the Canadaverse contribution forks, the former experimental preview,
open issues and pull requests, and the currently observable services. It follows
the operator's explicit decisions:

1. The Canadaverse preview is **upstream dev plus audited fixes**. It is no longer
   the union of every experiment.
2. **Every bug fix has a small, focused PR targeting dev.** The audit document is
   consolidated; the implementation proposals are independently reviewable.
3. Only Canadaverse is deployed by this work. Dev, dev1 and production are not
   deployment targets. Production acceptance belongs to the maintainer.
4. Removed interfaces do not authorize deletion of historical data, credentials,
   recovery copies or source branches.

The immediate priority is correctness under load: preserve evidence, bound work,
avoid misleading empty/successful responses, and make changes cheap to review.
New pages and larger experiments belong to the separate
[roadmap](roadmap-20261116.md), not implicitly in this baseline.

## What was inspected, and what this establishes

The inventory covers all seven repositories visible in the Beacon organization,
five relevant contribution/intake forks, all their open issue/PR discussions at
the recorded snapshot, and the main/dev/dev1/preview branch heads. Source review
followed ingest, persistence, maintenance, reads, caches, live fanout, web and
mobile consumers, native polling, accounts, alerts, deployment and recovery.

The verification combines source review, existing suites, new reproducing
regressions, PostgreSQL fixtures, CI, bounded read-only runtime measurements,
artifact checks and browser journeys. It is not a proof that every possible bug
has been found. A test fixture, a three-request latency sample and a browser
screenshot establish different things; none is a production capacity guarantee.

Private credentials, account records, channel contents, broker passwords and
private collector code are excluded from this public handoff. Detailed operator
receipts and backups remain private. The final delivery receipt identifies the
exact deployed revisions, PRs, checks, preserved data and rollback checkpoint.

### Code parity is not configuration parity

Upstream's native optional systems remain opt-in. Its account configuration accepts
an origin, not a URL subpath; observer firmware likewise documents a root-host
`poll.url`. Canadaverse currently serves Beacon under `/beacon-dev/`. A future
native account/polling rollout therefore needs a dedicated hostname or an explicitly
reviewed subpath contract, plus mail/portal settings and approved observers. A
MeshMapper regional catalogue key is not an OAuth client secret or an SMTP account.

The clean preview must not fake these prerequisites, enable public registration
without functioning verification, or run an independent collector alongside the
native election coordinator for the same radios.

### Evidence-specific limits

- A supported TRACE is structurally compatible, not authenticated. A suspect
  record does not prove radio corruption or a collision. Raw history remains.
- Ordinary packet path hashes use 1–3-byte widths. TRACE's payload flags encode
  power-of-two widths, and its wire path contains SNR bytes. The upstream MeshCore
  implementation makes this distinction in
  [Mesh.cpp](https://github.com/meshcore-dev/MeshCore/blob/main/src/Mesh.cpp).
- Scope configuration, heard scoped packets and confirmed forwarding evidence
  are different facts. Removing an experimental layer must not conflate them.
- Node activity counts hearings of packets attributed to an originating key, not
  every forwarded packet or the health of the node. Gaps do not prove downtime.
- Signal presence is preserved in storage; the existing aggregate zero/zero
  exclusion remains for legacy consistency. Old default-zero rows cannot be
  reliably reclassified as missing without original evidence.
- The clock-window regression establishes sequential insert and conflict
  behavior. It is not a claim that every concurrently inserted history is an
  exactly sized snapshot at every instant.

## End-to-end backend coverage

### Broker and ingest boundary

Reviewed broker subscription/routing, topic identity, country/IATA filtering,
queue admission, observer ordering, decode failures, duplicate reports, status,
neighbor snapshots and packet side effects. Keep two-broker deduplication and
receipt-time identity. A broker PUBACK is not an application storage receipt.

The observer backlog/replay question remains a separate contract. Timestamp
clamping is not permission to replay old traffic as newly heard traffic. Before
supporting replay, define immutable heard/received times, retention interaction,
deduplication lifetime, producer pacing, admission limits and an acceptance receipt.
Do not retrofit replay by changing all old timestamps to the current time.

### Identity, decoding and evidence

Reviewed advert discovery, prefixes, logical endpoints, route promotion, TRACE
parsing, neighbor evidence and capability updates. Full public keys remain the
identity; prefixes are observations requiring scoped candidate resolution. Do not
infer a unique repeater from a short hash simply because one map contains only one
matching marker. Raw packet evidence is retained when inferred topology is refused.

The protocol review does not justify a geographic distance cutoff without an
operator policy. Tropo/long links and missing coordinates are not automatically
corrupt. Configurable validation is tracked separately from the demonstrated
structural and ambiguity bugs.

### Database and maintenance

Reviewed high-volume IDs, cursor types, unique constraints, route retention,
read-model trust, packet sites, channel-message IATAs, rollup/raw-tail joins,
backfill pacing, migration identity, backup/export and pool roles. The prior
32-bit high-volume ID problem is fixed in the observed preview. Do not call
integer-backed reference tables a new imminent overflow without measuring their
allocation rate and remaining range.

Backfills need both correctness watermarks and work limits. A canceled transaction
must be rolled back before reuse, especially when a session holds an advisory
lock. Never advance a watermark after a failed slice. Smaller batches alone are
not a deadline; the statement itself needs a bound.

The new activity regression is important during rolling upgrades: a global
completed-hour marker predates a newly introduced rollup family. An empty new
table does not establish zero traffic. Longer-term per-family coverage metadata
would make that distinction explicit across every analytics page.

### API, caching and live delivery

Reviewed pagination, cursor binding, list caps, cancellation, query guards,
response encoding, Redis fallbacks, reference caching, websocket origin/ticket
checks, per-IP limits, send budgets and reconnect healing. Preserve bounded
labels on metrics; do not put node keys, channel contents, URLs or credentials
into metric dimensions.

Redis is an optimization, not permission to multiply database work during an
outage. Coalescing must survive both misses and errors. A shared fetch outliving
one disconnected caller still needs its own deadline. Returned values must not
share mutable handler state between clients.

### Native polling and requested telemetry

Reviewed policy/owners endpoints, claims, elections, freshness, per-observer
budgets, readings, trust flags, requested-target slots, password sealing and
retention. Upstream has a functioning server-side coordination design; it does
not require the separate agent scaffold. Evidence-based ranking remains based on
observer assertions, not hardware attestation. Use an explicit `polling.request_observers: approved` when
sharing requested-node credentials only with operator-approved observers.

The final upstream snapshot changes the documented request-observer default to
`all`. On an enabled instance that omits the setting, this can broaden which
evidence-bearing observers receive a requested node's sealed guest credential.
The service guard itself fails closed for values other than explicit `all` or an
approved observer. Treat the deployment setting as a release decision; do not
assume the former approved-only default survives an upgrade. Polling remains
disabled on the preview, so this audit does not enroll additional recipients.

Keep disabled firmware policy endpoints present and paused. A missing policy
route can invoke firmware fallback behavior. Do not run the retired companion
reservation system alongside native polling without a shared lease protocol.
Before migrating old measurements, map provenance, channel number, units and
missingness; do not relabel historical independent samples as natively trusted.

### Accounts, Atlas sync and alerts

Reviewed feature gates, password/hash bounds, session generations, reset/revoke
races, CSRF/origin checks, local versus portal accounts, Atlas conflict handling,
outbox retries, delivery expiry and evaluation cursors. Existing native account
and polling integration tests remain mandatory for backend fixes that change
shared router or storage behavior.

Account routes and telemetry credentials must not enter public query caches.
Keep public read caches separate from identity-bearing requests. The mobile
response-bound fix preserves this boundary and does not clear a valid session
because the server returned a large or stalled response.

Alerts have batching, cursor, attempt and age bounds. Successful evaluation is
not proof of email/push delivery. Notification acceptance requires a controlled
operator account and actual delivery evidence, not a test message to arbitrary users.

### MeshMapper and external providers

Reviewed API-key handling, import cadence, response bounds, redirect refusal,
ETag handling, failure cooldowns, cached metadata and source attribution. Preserve
regional key scoping and private backend storage; do not put keys in frontend
build variables. A failed refresh may leave cached data available, so age and
refresh state matter. Reassess cache authorization when credentials or regional
coverage change; provider policy needs to define whether old authorized snapshots
may remain public. The retired profile extension is not silently reintroduced as
part of this audit.

## Documentation and maintenance corrections

- The live inventory and review map supersede historical October preview
  manifests. Prepared branch heads are not deployed heads.
- High-level design language no longer promises a universal mobile 60 fps or
  conflates ordinary and TRACE path widths.
- Container log rotation is a separate focused operational patch. It does not
  alter retention of packets, readings, access logs or backups.
- The private archive and agent scaffold need a maintainer disposition. Archive
  status, bot shutdown and deletion are not performed merely because their names
  suggest retirement.
- Keep one public contract in beacon-docs and short implementation notes in code
  repositories. Avoid copying long competing roadmaps into every repository.

## Release and recovery requirements

1. Review and merge independent fixes in the order in the review map. Refresh any
   overlapping generated SQL/Swagger files after each prerequisite lands.
2. Require the final source commit's build, lint, tests, PostgreSQL checks, plan
   checks and relevant security checks. A green parent commit is not sufficient.
3. Build preview artifacts in Actions from the exact candidate. Verify revision,
   tree, source archive, binary metadata and asset hashes before switching.
4. Preserve the previous app, config, frontend, databases and retired intake
   history. No migration downgrade or historical evidence deletion is needed.
5. Verify brokers, representative reads, client journeys, feature exclusions,
   source offer and saved Atlas state. Test a recovery path before claiming one.
6. Keep the public native polling policy paused until a reviewed hostname and
   observer enrollment are available. Check the removed independent routes fail
   closed; do not leave an accidental direct proxy to a retired intake.
7. Promote to dev/live only through the maintainer's acceptance and deployment
   process. Dev1's 502 must be resolved separately by its operator.
